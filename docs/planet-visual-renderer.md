# Planet Visual Renderer Architecture

## Scope

Universus planet visuals should be generated by a deterministic Rust renderer, not by runtime AI image generation. Stable Diffusion or similar tools may still be useful for one-off concept art and palette exploration, but they must not be part of the authoritative gameplay asset path. The production path needs reproducible output from `universe_id`, `planet_id`, coordinates, planet class, and a renderer version so overview pages, galaxy thumbnails, caches, tests, and replays all resolve to the same image.

The current Rust prototype lives in `crates/game-planet-visuals`. It already exposes:

- `PlanetVisualProfile`: seeded visual metadata such as catalog/archetype keys, planet class, scale band, radius, density/gravity hints, ocean/ice/cloud/atmosphere fractions, rings, palette, and render model.
- `PlanetRenderer::render_icon`: square transparent orbital planet thumbnail output.
- `PlanetRenderer::render_banner`: current overview-banner entrypoint. It now delegates to the terrain overview renderer instead of reusing the orbital banner.
- `PlanetRenderer::render_terrain_overview_with_*`: aspect-aware surface/sky establishing image using a deterministic map anchor, raymarched heightfield, footprint-filtered materials, geometric water Fresnel, finite-shell volumetric clouds, atmosphere, rings, moons, and stars.
- `PlanetRenderer::render_orbital_banner_with_*`: explicit orbital/full-globe banner with space background, rings, planet, and moon.
- `PlanetRenderer::render_surface_map`: equirectangular albedo/surface texture output.
- `PlanetRenderer::render_reflection_map`: lat-long reflection/environment map output.
- `PlanetRenderer::render_normal_map`, `render_height_map`, `render_vegetation_map`, `render_roughness_map`, `render_ambient_occlusion_map`, and `render_horizon_occlusion_map`: exported material-map products, with compatibility `render_surface_*` aliases.
- `render_planet` binary: writes prototype PNGs, profile JSON, preview HTML, optional material maps, and optional manifest data under `assets/planet-rust-prototype`.
- `scripts/prototype/render_planet_matrix.ps1`: batches the binary across presets, qualities, planet sizes, seeds, and requested archetype keys.

The architecture below keeps that crate as the owned rendering library and avoids pushing rendering logic into `app-web-frontend`, `app-api-gateway`, or route handlers.

## Current Implementation Status (2026-07-16)

Evidence checked for this status: `crates/game-planet-visuals/src/lib.rs`, `profile.rs`, `catalog.rs`, `modifiers.rs`, `backend.rs`, `gpu.rs`, `pathtrace.rs`, `src/bin/render_planet.rs`, `crates/game-planet-visuals/tests/*.rs`, and `scripts/prototype/render_planet_matrix.ps1`.

Blunt summary: the renderer is no longer just a square icon prototype. It has deterministic CPU raster outputs, a raymarched local heightfield overview, footprint-filtered water and terrain detail, volumetric cloud-shell integration, direction-space reflection environments, AO/horizon-occlusion products, a broad profile/catalog table, material-map exports, size presets, and tiled progress. The canonical prototype remains a CPU raster proof; production GPU acceleration and a fully path-traced archive renderer are still future work.

Implemented renderer outputs:

- `render_icon` produces a transparent square orbital thumbnail. It uses the shared generated maps, planet shading, atmospheric limb approximation, rings when present, sharpening, and optional downscale from native supersampling.
- `render_banner` currently means terrain overview, not orbital banner. It calls `render_terrain_overview_with_progress`.
- `render_terrain_overview_with_progress` produces an aspect-aware surface-level overview with a deterministic map anchor, a refined CPU heightfield raymarch, nine-probe limb classification, terrain/water footprint filtering, geometric water Fresnel and capillary detail, finite spherical-shell cloud integration, local shadows and occlusion, atmosphere, rings, moon, sparse stars, distance fog, and tone mapping.
- `render_orbital_banner_with_progress` remains available for a full-globe space-camera banner with procedural space background, rings, planet, and moon.
- `render_surface_map` exports an equirectangular albedo texture.
- `render_reflection_map` exports a lat-long direction-space environment/reflection map sampled from the procedural sky/sun/nebula function without image-space pole seams.
- `render_planet` writes day/night icons, day/night overview banners, surface and reflection maps, profile JSON, and preview HTML by default. `--emit-material-maps` adds normal, height, vegetation, roughness/wetness, ambient-occlusion, and horizon-occlusion maps. `--emit-physics-maps` adds physics and density maps. `--emit-manifest` adds a JSON manifest with byte lengths and SHA-256 hashes for every listed artifact.

### Canonical CPU proof and reproducibility

The approved `480p` canonical family under `assets/planet-rust-prototype` was produced from seed `0x5EED_1208_0001` with the CPU raster backend, the `ultra` quality tier, automatic worker selection, and an explicit supersample request of `3`:

```powershell
cargo build -p game-planet-visuals --release --bin render_planet
target\release\render_planet.exe --backend cpu --renderer raster --preset 480p --quality ultra --supersample 3 --progress quiet --emit-manifest --output-dir target\renderer-promotion-v29-final
```

The delivered products are a `854x480` day banner, `854x480` night banner, `480x480` day/night icons, and `960x480` surface/reflection maps. The effective native supersampling is `3x` for banners (`2562x1440`, nine spatial raster samples per delivered pixel) and `4x` for icons (`1920x1920`, sixteen spatial raster samples per delivered pixel); the maps render at native resolution. This is the raster path, so no path-tracing sample count applies. On the Windows reference run tied to the promoted files, the complete family took **70.089 seconds wall time** and **63.78 MiB peak RSS**.

Renderer AOV validation is intentionally separate from beauty generation:

```powershell
target\release\render_planet.exe --backend cpu --renderer raster --progress quiet --diagnostic-aovs-only --output-dir target\renderer-diagnostics-v29-final
cargo test -p game-planet-visuals --test terrain_diagnostic_aov_contract -- --nocapture
```

The diagnostic set is `320x180` at `1x`, with a shared nine-probe terrain/sky limb classifier in the transition interval and twelve finite-shell cloud integration steps. The final diagnostic CLI took **40.486 seconds wall time** and **38.92 MiB peak RSS** and reproduced all 14 approved diagnostic files byte-for-byte. The debug contract measured a `35.135/255` maximum atmosphere row jump, `2.894%` fractional-water coverage, `0.04703` Fresnel Laplacian, zero isolated Fresnel spikes, `157/255` cloud peak with `28.299%` occupancy, and `18.284/255` mean geometric-to-shading-normal delta.

The canonical manifest is an integrity contract: each image, profile, and preview entry records its byte length and SHA-256 digest. It intentionally omits machine-specific output directories and paths. `canonical_asset_contract` re-reads the promoted files, checks PNG dimensions and preview references, and rejects manifest/hash/profile drift.

Implemented material-map data:

- Internal generated maps include albedo, height, water, clouds, city-light signal, vegetation, biome, roughness, and wetness.
- Exported map functions are `render_normal_map`, `render_height_map`, `render_vegetation_map`, `render_roughness_map`, `render_ambient_occlusion_map`, and `render_horizon_occlusion_map`.
- Compatibility aliases exist for `render_surface_normal_map`, `render_surface_height_map`, `render_surface_biome_map`, and `render_surface_roughness_wetness_map`.
- Material-map tests require deterministic, opaque, nonblank, correctly sized normal, height, vegetation/biome, roughness/wetness, ambient-occlusion, and horizon-occlusion outputs.
- Not implemented as exported products yet: `surface_metallic`, dedicated `surface_emission`, `material_id`, separate `cloud_alpha`, and dedicated foam/snow/ice/dust/lava heat maps.

Planet type, modifier, and catalog coverage:

- `catalog.rs` and `modifiers.rs` provide broad family coverage, more than 100 typed modifiers, unique IDs, scale metadata, and tests for major family coverage.
- `profile.rs` has a weighted and forced `PLANET_TYPE_MATRIX` for Mercury/Mars/Venus analogs, ocean/low-water/megacontinent/archipelago/ice-age/greenhouse/post-apocalyptic variants, volcanic/lava/sulfur/acid-cloud worlds, carbon/diamond/iron/chthonian worlds, super-Earth/sub-Neptune/gas-dwarf/gas-giant/hot/cold/Saturn-like/sulfur-rain/diamond-rain/ammonia-storm/ice/helium/puffy giants, rogue/tidally locked/twilight/circumbinary/eccentric worlds, proto/dwarf/exomoon/captured moon entries, and artificial/ecumenopolis entries.
- The raster renderer now has archetype-specific visual contracts for ultra-vs-standard color strength, gas giant variant banding/storm signatures, sulfur/acid/carbon/ice family separation, ocean artifact rejection, terrain realism, and material-map exports.
- This is real catalog/profile and renderer coverage, not final physically complete simulation. A catalog row being present still does not mean final gas giant fluid dynamics, Venus deck chemistry, Mars dust transport, artificial-world geometry, or production GPU parity is complete.

Resolution, aspect, and 8K guardrail:

- Library presets include widescreen 480p/720p/1080p/4K/8K, square 512/1024/2048/4096, and portrait 720p/1080p/4K.
- The `render_planet` binary exposes 11 user presets: `480p`, `720p`, `1080p`, `4k`, `8k`, `square-1k`, `square-2k`, `square-4k`, `vertical-720p`, `vertical-1080p`, and `vertical-4k`.
- The terrain overview camera is aspect-aware. Portrait, square, and landscape renders change the horizon and framing instead of just stretching pixels.
- Native render validation defines an 8K guardrail of 7680x4320 and 33,177,600 pixels. Oversized native dimensions are rejected by `validate_render_size`, and supersampling is clamped so 8K and 4096-square outputs do not exceed the native budget.
- Important caveat: validation is not uniformly enforced at every public render entrypoint yet. The binary's 8K equirectangular map dimensions are 8640x4320 for 2:1 maps, so map sizing and the native 8K guardrail still need a final product-by-product policy.

Multithreading and progress:

- Tiled rendering exists through `TilePlan`, `RenderExecutionMode`, and `render_tiled_into_canvas`.
- `Automatic` uses `thread::available_parallelism`; `MultiThreaded { threads }` honors an explicit thread count; `Serial` forces one worker.
- Surface map, reflection map, normal map, height map, vegetation map, roughness map, terrain overview, and space-background phases can render by tiles and emit progress.
- Progress events include phase, tile, completed tiles, completed pixels, total pixels, execution mode, and worker count. The CLI supports `--progress human|json|quiet` and `--threads <count>`.
- The icon path is effectively serial today. Orbital banner background can be tiled, but the planet/rings/moon drawing phases are still serial canvas operations.

Still-not-final realism gaps:

- AO/horizon occlusion: deterministic AO and horizon-occlusion maps are exported and sampled by the CPU raster path. They remain approximations rather than path-traced cavity and sky-visibility solutions.
- Backdrop/deep space: there is procedural sky/star/sun/moon/ring/aurora/background work, but not a physically coherent backdrop system. Multi-star lighting, orbital body placement from real orbital data, a structured galaxy plane and dust model, eclipses, orbital debris, and cache-keyed backdrop descriptors remain planned.
- Terrain-level overview: the banner now raymarches a local heightfield and resolves displaced horizon silhouettes with footprint-filtered detail. It does not yet provide mesh/displacement interchange, path-traced terrain, authored landmark IDs, gas-giant upper-atmosphere cameras, or a serialized `surfaceCamera` manifest block.
- Atmosphere and lighting: current Rayleigh/Mie limb, terrain haze, and finite-shell volumetric clouds are bounded CPU approximations. Explicit per-gas scattering profiles, multiple scattering, cloud self-shadow integration, multi-star lighting, and physically calibrated exposure/bloom remain planned.
- Ray tracing/path tracing: the CPU tracer is wired for bounded icons and explicit preview artifacts. It supports deterministic tiled sampling, bounded bounce depth, reflection/refraction feature controls, procedural surface models, direct-light/occlusion terms, and sampled atmosphere/limb optics. The canonical V29 icon/banner family still uses the CPU raster path, and there is no full path-traced terrain banner or archive-quality planet product yet.
- GPU: `gpu.rs` currently only defines a `WgpuBackend` marker. There is no implemented `wgpu` raster/raymarch/path-trace backend producing renderer outputs.

## Renderer Model

`game-planet-visuals` should own a physically based procedural renderer. The input is a compact `PlanetVisualProfile`, and the output is a set of PNG/WebP-ready raster products plus metadata. The renderer should not store opaque prompt strings as the source of truth; it should store structured knobs that can be serialized, hashed, migrated, and tested.

Core modules to split out as the prototype grows:

- `profile`: creates `PlanetVisualProfile` from game data and stable seeds.
- `maps`: generates albedo, height/altitude, normal, vegetation/biome, water/wetness, roughness, cloud-alpha, emission/city-light, AO/horizon-occlusion, ring, and atmosphere control maps.
- `materials`: converts map samples into PBR material parameters such as base color, roughness, metallic, emission, transmission, and phase coefficients.
- `cpu`: contains the current raster/sphere renderer and the future CPU path tracer.
- `gpu`: optional future backend using the same profile, maps, camera, light, and material structs.
- `outputs`: writes icons, thumbnails, overview banners, surface maps, reflection maps, manifests, and cache metadata.

The first production renderer can remain "PBR-ish" raster shading, matching the current prototype: relief normals from height maps, Lambert/Oren-Nayar land shading, water Fresnel/specular response, cloud shadows, city lights on the night side, ACES tone mapping, and deterministic rings/moons. The important boundary is that the data model should already look like a renderer contract, not a frontend drawing helper.

## Archetype And Modifier Roadmap

The renderer should support hundreds of planet looks by composing a bounded archetype catalog with a deterministic modifier stack. The goal is not hundreds of hand-authored renderers. It is a structured visual taxonomy where each archetype owns the physical baseline and each modifier changes a narrow, testable part of the profile, maps, materials, camera, or backdrop.

Archetypes should be broad enough to give stable player expectations:

- Rocky terrestrial: Earth analog, super-Earth, dry desert, ocean world, ice world, tundra, jungle, mountain-heavy, cratered, tidally locked, rogue, and tomb variants.
- Inner-system analogs: Mercury analogs with no atmosphere and extreme crater/terminator contrast; Mars analogs with iron-rich regolith, dunes, canyons, dust haze, dry channels, and polar caps; Venus analogs with dense greenhouse atmosphere, sulfur clouds, orange haze, and pressure-smoothed terrain visibility.
- Volcanic worlds: basalt plains, lava fissures, caldera fields, ash deserts, plume systems, glowing night-side lava, sulfur flats, and resurfaced young crust.
- Gas giants and ice giants: banded, storm-heavy, ringed, auroral, pale methane, deep blue, hot Jupiter, inflated, brown-dwarf-adjacent, and compact mini-Neptune looks.
- Exotic exoplanets: eyeball worlds, lava super-Earths, carbon planets, iron-rich worlds, ocean super-Earths, multi-star systems, high-obliquity seasons, cold rogue planets, and irradiated hot-side/cold-side split worlds.
- Civilizational/post-apocalyptic variants: settled, ecumenopolis hints, terraformed, polluted, orbital-industrial, scarred by impacts, glassed deserts, dried oceans, ruined city-light networks, ash winter, runaway greenhouse aftermath, and biosphere collapse.

Modifiers should be typed and ordered. A planned stack order:

1. `identity`: universe, star system, planet identity, seed, renderer version, and output family.
2. `orbital_context`: star type, multi-star lighting, distance, phase, rings, moons, tidal lock, obliquity, and local sky visibility.
3. `bulk_body`: radius, gravity, flattening, composition, ocean budget, ice budget, volatile budget, and magnetic/aurora potential.
4. `archetype_base`: primary archetype and family-specific defaults for maps, materials, atmosphere, and output expectations.
5. `geology`: plate activity, impact age, crater density, volcanism, erosion, mountain frequency, canyon masks, lava tubes, and sediment layers.
6. `hydrology_cryosphere`: oceans, shorelines, rivers, dunes, glaciers, sea ice, frozen lakes, brine flats, and dry seabeds.
7. `atmosphere_weather`: pressure, scattering coefficients, haze, clouds, dust storms, sulfur decks, lightning, precipitation, aurora, and gas giant band flow.
8. `biosphere_civilization`: vegetation, reef/algae tint, city lights, agricultural grids, orbital shadows, industrial haze, and settlement scars.
9. `catastrophe_history`: impact scars, bombardment, firestorms, nuclear/ash winter, climate collapse, runaway greenhouse, terraforming failure, and ruined infrastructure.
10. `local_surface_detail`: overview-banner biome anchor, heightfield octave settings, local landmarks, foreground material distribution, camera pose, and horizon composition.
11. `render_product`: output kind, target size, camera class, backdrop policy, quality tier, backend, tone map, and downscale filter.

The ordered stack must be serialized in normalized form. Cache keys should include the normalized stack hash plus each referenced algorithm version. If a modifier only affects gas giant cloud flow, it should not perturb unrelated rocky-world maps; if it affects shared lighting, it must be part of every output key that sees that lighting. This keeps the catalog large without causing uncontrolled cache churn.

The matrix is a contract for catalog and test coverage. A new archetype family should add or update a row in this table, add normalized taxonomy entries, add at least one deterministic manifest fixture, and add image-level smoke coverage for every supported output family. A renderer release should not claim hundreds-of-types support from combinatorics alone; coverage requires tested base families plus tested modifier composition across the matrix.

## Output Families

Planet visuals are not one interchangeable render at different sizes. The overview banner is a terrain-level/surface establishing view for the selected planet. It should use a terrain camera placed close enough to show local landforms, coastlines, ice, vegetation, or settlement hints while still framing the horizon and atmosphere as first-read signals. The surface view should sample a local biome patch from the deterministic maps, then shade it with local altitude changes, terrain normals, vegetation masks, water/wetness masks, roughness, reflections, cloud shadows, emission/city lights, and sky visibility. Rings and moons should appear in the sky when the profile supports them, with their placement derived from the same orbital data used by other outputs.

Orbital planet renders are separate products. `PlanetIcon`, `GalaxyThumbnail`, and future detail/orbital outputs should keep the external space-camera view of the full globe, rings, moons, phase, and transparent or compact backgrounds. They are optimized for recognition in dense UI surfaces, not for establishing what it feels like to stand near the planet surface.

This distinction should be visible in cache output names and manifests. The overview/banner cache product is a wide surface-establishing raster, for example `overview-banner`, with terrain camera, sampled biome region, horizon, atmosphere, sky objects, and reflection settings included in the output metadata hash. Galaxy thumbnails are compact orbital products, for example `galaxy-thumbnail`, with globe camera framing, alpha/background policy, and UI-scale downsampling in their own cache entries. A cache hit for one output family must never be reused as the other.

## Ultra-Realistic Surface Overview Rendering

The final overview banner should be a cinematic surface-level image generated from the same deterministic planet data as the orbital outputs. It should not be a flat surface texture with a sky gradient. The planned rendering path is:

1. Select a deterministic surface anchor from the profile: latitude, longitude, biome/material region, time/phase, camera altitude, look direction, focal length, and horizon target.
2. Build a local terrain tile from global maps plus high-frequency procedural detail: height, slope, curvature, erosion, water depth, snow/ice thickness, lava crust, dust, rock strata, vegetation/city masks, and feature IDs.
3. Render the foreground with a heightfield or raymarched surface camera. A fast raster heightfield is acceptable for previews; the high-quality path should raymarch or path trace displaced terrain so ridgelines, craters, dunes, lava channels, glaciers, and shorelines have real silhouettes.
4. Shade materials from explicit map products: albedo, height/altitude, normal, vegetation/biome mask, water/wetness, roughness, metallic, cloud alpha/shadow, emission/city lights, AO/horizon occlusion, foam, snow, ice, dust, ash, lava heat, and material ID.
5. Add atmosphere and weather in depth order: ground fog, dust/sulfur haze, cloud shadows, storm fronts, volumetric shafts where affordable, and horizon scattering.
6. Composite deterministic sky/backdrop elements: sun or suns, moons, rings, aurora, galaxy plane, nebula color wash, starfield, orbital debris, and distant bodies.
7. Apply physically motivated post-processing: exposure, ACES or equivalent tone mapping, bloom only from emissive/lava/city/highlight sources, color management, and final anti-aliased downscale.

Surface overview outputs should carry a `surfaceCamera` block in the manifest. That block should include camera pose, anchor coordinates, field of view, near/far ranges, terrain tile resolution, raymarch/pathtrace mode, local map algorithm versions, backdrop seed, and any selected landmark IDs.

## Backdrop Rendering

Backdrop rendering should be owned by the renderer, not by the frontend. The backdrop is part of the planet image because it affects lighting, silhouettes, atmosphere color, and player perception of scale.

The backdrop system should generate:

- Stellar disk and light data: sun size, color temperature, angular position, phase, eclipse state, multi-star contribution, and visible glare/bloom masks.
- Orbital bodies: moons, ring arcs, nearby planets, occultations, shadow lines, and deterministic placement consistent with orbital data.
- Deep-space background: starfield, galaxy plane, nebula tint, dust lanes, and optional local system features.
- Civilization/catastrophe overlays where appropriate: orbital debris, station silhouettes, war scars, artificial rings, and falling debris streaks.

Backdrop layers should be output-family aware. Orbital thumbnails may use transparent or compact UI backgrounds; overview banners should use a sky/backdrop layer tied to the surface camera. Every backdrop-affecting parameter belongs in the cache key for outputs that include it.

## CPU Path Tracing

The high-quality offline path should be a CPU renderer first. That keeps CI and asset generation portable across Windows, Linux, and headless workers without depending on GPU availability.

Implementation direction:

- Use a tile-based renderer so overview banners and thumbnails can render in chunks and report progress.
- Keep all randomness seeded from the render manifest; no thread-local nondeterminism.
- Support sample counts by quality tier: `preview`, `standard`, `high`, and `archive`.
- Use progressive accumulation internally, then write the final downscaled image only after all tiles pass.
- Make path tracing additive to the current renderer: the fast raster path stays available for tests, local previews, and fallback generation.

The CPU path tracer should use the same material inputs as the raster path. Initial bounces can be limited to direct lighting, hard/soft shadows, atmosphere shell samples, water reflection, and ring/moon occlusion. Full global illumination is not required for game UI assets.

## Future GPU Backend

A GPU backend should be introduced only after the CPU renderer and cache contract are stable. The likely Rust path is `wgpu`, behind an optional crate feature or sibling backend module, using the same `PlanetVisualProfile`, generated maps, output manifests, and quality settings.

The GPU backend is a performance backend, not a second visual system. It must produce visually compatible images for the same profile and renderer version, even if exact floating-point pixels differ. Tests should compare nonblank output, alpha coverage, histogram ranges, and golden metadata rather than requiring byte-identical CPU/GPU PNGs.

Backend strategy:

- CPU raster remains the fastest deterministic preview/test path.
- CPU path tracing becomes the canonical high-quality offline path for archive assets, screenshots, and production banners where GPU access is not guaranteed.
- GPU raster/raymarching accelerates local previews, batch generation, and eventually high-volume asset production.
- CPU and GPU backends must consume the same profile, modifier stack, maps, material descriptors, camera descriptors, backdrop descriptors, and output manifest.
- Cache keys include `backend`, but renderer manifests should also record a backend compatibility class so the system can decide when a GPU preview is visually acceptable while a CPU archive render is still pending.

## Ray Tracing And Reflection Maps

Ray tracing should be used where it pays off in UI assets:

- Planet limb, ring, and moon occlusion.
- Cloud and terrain self-shadowing at banner scale.
- Ocean reflection and glints based on the sun/view half-vector.
- Optional reflection maps for higher quality water, ice, and metallic station overlays.

Reflection maps should be generated as cacheable renderer products, not recomputed in route handlers. A practical contract is:

- `surface_albedo`: equirectangular base color.
- `surface_altitude`: normalized elevation, local relief, bathymetry/depth where applicable, and overview anchor altitude hints.
- `surface_normal`: tangent-space or world-space normal map derived from height/altitude plus local detail.
- `surface_biome`: vegetation, biome, reef/algae, crop, ruin, settlement, and catastrophe masks.
- `surface_water_wetness`: ocean/lake depth, shoreline wetness, foam, ice, brine flats, saturated soil, and reflective puddle hints.
- `surface_roughness`: material roughness, gloss, water/ice smoothness, dust, glassed terrain, and industrial/artificial surfaces.
- `cloud_alpha`: high-altitude cloud coverage, storm opacity, cloud shadow strength, and compositing alpha.
- `surface_emission`: lava, fires, city lights, industrial heat, aurora spill, and night-side civilization networks.
- `surface_ao`: baked crater, canyon, ridge, ruin, boulder, and local curvature occlusion.
- `horizon_occlusion`: low-resolution sky-visibility and horizon mask for surface cameras.
- `reflection_env`: compact lat-long or cube environment map for water/rings.

The overview banner can then sample these products through either the raster path or the path tracer.

## Material Maps And Ambient Occlusion

The material-map contract should grow beyond the current prototype surface map. These are renderer-owned products, not frontend decorations. They are generated from the profile, archetype, modifier stack, and stable seeds, then reused by icons, orbital thumbnails, surface maps, overview banners, and path-traced archive renders where appropriate.

Required material map products:

- `surface_height` / `surface_altitude`: global elevation, local relief controls, bathymetry/depth, mountain/crater/ridge displacement, and overview camera altitude constraints.
- `surface_albedo`: base color after archetype, biome, geology, and catastrophe modifiers.
- `surface_normal`: generated from height/altitude, local detail, crater rims, dunes, lava crust, ice ridges, erosion, and artificial geometry hints.
- `surface_biome`: vegetation, biome class, reef/algae, crop, settlement, ruin, ash-burn, terraforming, and catastrophe masks.
- `surface_water_wetness`: oceans, lakes, rivers, water depth, foam, shore wetness, wet soil, reflective puddles, sea ice, glacier coverage, snowpack, brine, and chemical flats.
- `surface_roughness`: dry rock, dust, water, ice, glassed terrain, metallic deposits, wet surfaces, vegetation, and city/industrial materials.
- `surface_metallic`: rare for natural terrain but useful for metallic worlds, exposed ore, megastructures, and artificial overlays.
- `surface_emission`: lava, city lights, fires, aurora spill, industrial heat, active machinery, and post-apocalyptic burn scars.
- `surface_ao`: baked map-space occlusion from height/altitude, crater density, canyon walls, boulder fields, city ruins, vegetation density, and local terrain curvature.
- `horizon_occlusion`: surface-camera sky visibility, terrain horizon blocking, ridge/canyon silhouettes, city canyoning, and ring/moon/sun occlusion hints.
- `cloud_alpha`: low/high cloud coverage, storm opacity, cloud height, phase, dust/sulfur/ash layers, cloud-shadow controls, and compositing alpha.
- `material_id`: compact IDs for terrain classes so renderers can branch without re-deriving classification from color.

How these maps drive realism in the terrain overview:

- Altitude and height maps displace the overview terrain, select plausible camera elevation, create ridgelines and crater rims, and drive snowline, fog, cloud-shadow, and atmospheric depth decisions.
- Normal maps add small-scale lighting response so dunes, lava crust, ice ridges, eroded rock, and ruin edges catch light even when the preview path does not fully displace every detail.
- Vegetation and biome masks select ground cover, tint albedo, alter roughness, influence atmospheric humidity/haze, and let the camera find readable forests, tundra, farms, reefs, ash fields, or dead zones.
- Water and wetness maps decide where surfaces become reflective, where shorelines foam or darken, where ice/glacier materials replace liquid water, and where path tracing should spend samples on glints and refraction-like response.
- Roughness maps control specular spread across dry regolith, wet coastlines, ice, glassed terrain, metallic/artificial surfaces, and vegetation so reflections look material-specific rather than globally shiny.
- Cloud alpha maps cast moving-looking but deterministic cloud shadows, soften direct light under storm decks, provide height-separated compositing, and let thick atmospheres obscure terrain without baking clouds into albedo.
- Emission and city-light maps create night-side readability, lava/fissure bloom, industrial heat, settlement networks, and post-collapse broken grids while still participating in exposure and path-traced direct lighting.
- AO and horizon occlusion maps ground foreground terrain, darken craters/canyons/ruins/vegetation clusters, shape contact shadowing, and tell the path tracer where local terrain blocks sky, suns, rings, moons, or bright clouds.

Ambient occlusion should be layered:

- Baked map-space AO for craters, canyons, lava tubes, eroded terrain, megacity ruins, and dense rock fields.
- Horizon/sky-visibility AO for the surface camera so valleys, crater interiors, and urban ruins feel grounded.
- Contact AO in the raster path for foreground rocks, shorelines, snow/ice edges, lava crust, and artificial structures.
- Path-traced AO as the high-quality mode, seeded and sampled through the same tile system as the rest of the CPU path tracer.

AO algorithms and quality settings affect pixels, so their versions and sample counts belong in the cache key. If AO is disabled for a preview tier, that must also be represented in the manifest.

## Atmosphere

Atmosphere should be modeled as a shell around the planet with deterministic parameters from `PlanetVisualProfile`:

- `atmosphere_density` controls optical depth.
- Rayleigh color is driven by gas profile and produces the blue limb.
- Mie scattering handles haze, sunset/orange terminator glow, and dense storm worlds.
- Terminator softening should happen in the atmosphere layer rather than by flattening surface lighting.

The current prototype already approximates Rayleigh/Mie at the limb. The next step is to make those coefficients explicit in `PlanetVisualProfile` or a derived `AtmosphereProfile` so frozen cache keys can track visual changes.

## Clouds

Clouds should be separate layers above the surface instead of being baked directly into albedo:

- Low cloud alpha: broad weather systems and storm bands.
- High cloud alpha: wispy detail and polar circulation.
- Cloud normal/height: enough depth to cast shadows and catch rim light.
- Cloud motion phase: optional animation input for future frontend effects, but static outputs must remain deterministic.

For static UI assets, the renderer should composite cloud layers during output generation and also be able to export `cloud_alpha` for future animated or parallax frontend use.

## World Family Rendering Roadmap

Gas giants need a separate rendering model from rocky planets. They do not have a hard visible surface, so `render_surface_map` should represent pressure-level cloud/material layers rather than terrain. Overview banners for gas giants should use an upper-atmosphere or orbital-skimming camera: layered storm bands, vortices, cloud towers, ring shadows, aurora curtains, lightning, and deep haze. Cache metadata should record the pressure layer, band-flow algorithm, storm IDs, and camera altitude class.

Volcanic worlds should combine terrain and emissive materials: basalt plains, fresh lava, older cooled lava, sulfur deposits, ash falloff, plume columns, heat haze, black sand, and glowing fissures. The night side and surface overview path need `surface_emission`, `lava_heat`, plume shadowing, and bloom controlled by physically plausible exposure rather than manual glow overlays.

Venus, Mars, and Mercury analogs should be first-class archetype families because players recognize them quickly:

- Venus analog: dense atmosphere, high Mie scattering, sulfur cloud decks, orange/amber sky, muted terrain contrast, soft shadows, high-pressure haze, and corrosive weathering.
- Mars analog: low atmosphere, iron oxide palette, cold dust haze, dunes, dry channels, canyon systems, polar caps, dust storm variants, and blue/orange sunset edge cases.
- Mercury analog: no meaningful atmosphere, crater saturation, regolith roughness, extreme day/night thermal contrast, long sharp shadows, and stark black-space backdrops.

Exoplanets should come from physically parameterized extremes rather than arbitrary color swaps. Hot Jupiters need star-facing bloom, cloud shear, and day/night chemistry shifts. Tidally locked rocky worlds need hot-side melt/dryness, cold-side ice, terminator habitability bands, and strong horizon temperature gradients. Carbon, iron, ocean, and mini-Neptune worlds should change map generation, material maps, atmosphere, and backdrop lighting together.

Post-apocalyptic variants should be modifiers that can sit on top of many archetypes. Examples include impact winter, industrial collapse, glassed equatorial belts, dried oceans, ash-coated ice, ruin grids, broken city-light networks, orbital debris, runaway greenhouse aftermath, bio-collapse, and failed terraforming. These variants should alter maps and materials, not just add a color filter.

## Anti-Aliasing And Downscaling

Planet assets should render above target resolution and downscale to final sizes:

- Thumbnails/icons: render at 2x or 4x, then downscale with a high-quality filter.
- Overview banners: render at least 1.5x for production, 1x for preview.
- Path-traced outputs: combine sample accumulation with spatial supersampling before downscale.
- Alpha edges: downscale premultiplied alpha to avoid dark halos around transparent thumbnails.

This should replace ad-hoc sharpening as the main quality path. Sharpening can remain a final optional pass, but the default artifact should be anti-aliased by construction.

## Cache And Versioning

Rendered assets should be treated as derived artifacts. The cache key must include every input that can affect pixels:

- `renderer`: crate name plus renderer semantic version, for example `game-planet-visuals@0.1.0`.
- `algorithm`: profile/map algorithm, such as `procedural-planet-rust-v1`.
- `backend`: `raster-cpu`, `pathtrace-cpu`, or future `wgpu`.
- `quality`: sample count, supersampling factor, tone map, and downscale filter.
- `input`: universe ID, planet ID, coordinates, seed, planet class, and serialized profile hash.
- `taxonomy`: archetype ID, archetype version, ordered modifier stack hash, and modifier algorithm versions.
- `maps`: material-map set, map resolutions, AO settings, atmosphere/cloud algorithms, gas giant pressure layer, and local terrain tile settings.
- `camera`: output-family camera descriptor, surface anchor, orbital phase, field of view, and backdrop policy.
- `output`: kind, width, height, format, and color space.

Suggested manifest shape:

```json
{
  "cacheKey": "planet:...",
  "renderer": "game-planet-visuals@0.1.0",
  "algorithm": "procedural-planet-rust-v1",
  "backend": "raster-cpu",
  "quality": "standard",
  "outputs": {
    "planetIcon": "assets/planet-cache/.../planet-icon.png",
    "galaxyThumbnail": "assets/planet-cache/.../galaxy-thumbnail.png",
    "overviewBanner": "assets/planet-cache/.../overview-banner.png",
    "surfaceMap": "assets/planet-cache/.../surface-map.png"
  }
}
```

Cache invalidation should be version-forward: a renderer version bump or algorithm bump creates new artifacts instead of mutating old paths. `platform-cache` can hold hot metadata and lookup state, while durable files or object storage hold the actual raster outputs.

The modifier stack has direct cache impact. The stack must be normalized before hashing so equivalent inputs produce the same key, but the normalized representation must preserve ordering where ordering affects pixels. Examples:

- `venus-analog + post-apocalyptic-runaway-greenhouse` is not the same as `post-apocalyptic-dust-winter + venus-analog`.
- `mars-analog + polar-caps + dust-storm` should perturb atmosphere, clouds, albedo, and overview sky keys.
- `gas-giant + great-storm + ring-shadow` should perturb cloud-layer, backdrop, and orbital render keys but not create unused rocky heightfield products.
- `tidally-locked-exoplanet + terminator-habitable-band` should perturb local surface camera selection because the overview banner should prefer the terminator region when that modifier is active.

Preview and archive renders can share high-level profile/cache metadata, but their output keys must differ by backend, quality, sample count, map resolution, AO policy, and downscale filter.

## Integration Points

Frontend and API crates should consume renderer products, not recreate planet visuals.

- `app-api-gateway`: exposes planet visual metadata and signed/static asset URLs alongside `/api/planets`, galaxy, and overview responses.
- `app-web-frontend`: uses the overview banner and thumbnail URLs in the existing `/overview` and `/galaxy` pages.
- `game-galaxy` and `game-universe`: provide stable coordinates, universe settings, and placement context for profile generation.
- `platform-cache`: stores resolved manifests and prevents repeated generation for hot planets.
- `platform-worker-runtime`: runs async/batch render jobs when a cache miss is too expensive for request time.

Request-time behavior should be:

1. API asks for visual manifest by planet identity and requested output kind.
2. Cache hit returns URLs and metadata immediately.
3. Cache miss enqueues or runs a bounded preview render depending on quality and route.
4. Frontend receives either the finished asset URL or a stable placeholder keyed by the same profile.

The current `render_banner` function should be treated as the prototype entrypoint for `OverviewBanner`, meaning the surface-establishing output described above. It should not be reused for `GalaxyThumbnail`. `render_icon` maps to `PlanetIcon`, while `GalaxyThumbnail` and future orbital detail renders should use explicit orbital output kinds with their own camera, background, and downsampling policy.
